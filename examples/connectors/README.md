# examples/connectors/

Worked configurations for the connectors that talk to something outside this repo.

**These are not runnable fixtures.** Unlike [`../auto_toggle/`](../auto_toggle/), every one
of them needs hardware or a service on the other end, none produces golden output, none is
checksummed by [`../MANIFEST.json`](../MANIFEST.json), and none is regenerated by
[`../generate.py`](../generate.py). They exist so you can see the shape of a connector's
options without reading its schema file.

| File | Connector | Needs |
|---|---|---|
| [`modbus_tcp.json`](modbus_tcp.json) | `modbus_tcp` | A Modbus TCP meter or gateway, and `pip install -r requirements-modbus.txt` |
| [`home_assistant.json`](home_assistant.json) | `home_assistant` | A Home Assistant instance + a long-lived token, and `pip install -r requirements-homeassistant.txt` |
| [`openems.json`](openems.json) | `openems` | An OpenEMS Edge with `io.openems.edge.controller.api.rest` enabled |
| [`lorawan.json`](lorawan.json) | `lorawan` | A LoRaWAN network server publishing to MQTT (ChirpStack, The Things Stack, …) and at least one joined node. **No extra dependency** — it is MQTT, and paho is core |
| [`lora.json`](lora.json) | `lora` | A LoRa radio on a serial port of this machine, and `pip install -r requirements-lora.txt` |

The two LoRa entries are the same protocol reached two ways, and the choice is not close:
`lorawan` talks to a **network server**, which has already abstracted every gateway and every
end-node radio, so the EMS needs no radio of its own and nothing outside the core. `lora`
drives a **module wired to this host** and exists for point-to-point links that have no
network server at all. Both feed the same `lora` / `lora_switch` device, whose payload map is
configuration — one device class covers every node model behind either transport.

Each config declares a `csv_file` storage backend and the `AutoToggle` algorithm, so it is
a complete run rather than a fragment — point `main.py` at one and it will start, poll, and
write to `data/storage/`:

```bash
python main.py --config examples/connectors/modbus_tcp.json
```

With nothing on the other end you still get a useful result: the connector constructs,
reports its configuration warnings, fails to connect, and backs off on a doubling ladder —
**without** crashing the supervisor and without a traceback. That is worth watching once,
because it is what a site looks like when a meter is unplugged.

`Ctrl-C` in that state returns promptly. Each of these configs declares `required_devices`,
so `AutoToggle` is sitting in its readiness gate waiting for a device that will never become
ready — it notices the stop within a poll slice rather than holding it for the whole
`wait_for_devices_timeout`.

## Backtesting any of them

Every device here parses a string, and the string is exactly what its connector puts on the
wire. So each of these can be replayed with no hardware at all — swap the connector for a
`pseudo` one declaring `emulates`, and the devices cannot tell the difference:

```json
{
	"name": "replay",
	"protocol": "pseudo",
	"options": {
		"replay_file": "my_capture.csv",
		"emulates": "modbus_tcp",
		"speed": 0
	}
}
```

The replay file's `payload` column then carries the same JSON the live connector produced —
for `modbus_tcp` that is `{"blocks": {...}}`, for `openems` the Edge's channel response, and
for `home_assistant` a state object with the `entity_id` in the `topic` column. The
replay options are documented in [`../../connectors/pseudo.schema.json`](../../connectors/pseudo.schema.json).

## Secrets

Credentials are written as `${VAR}` and resolved from the environment at load time — never
commit a token or a password into a config file. See [`../../.env.example`](../../.env.example)
for the variables each connector expects and what they are worth to an attacker.
