# Motrix Edge

## Context
The goal of this project is to build a flexible and extensible EMS to optimize energy consumptions and other.

The goal of the architecture is, in one hand, to allow the writing of algorithms without caring about the
underlying IT architecture. In the other hand, to allow the writing of the underlying architecture without
caring about the algorithms.

The goal is to allow the writing of algorithms and the underlying architecture in parallel, allowing
the same algorithm to be used in different environments without changing the code.

## Implementation
To reach the goal, the architecture is based on the following components:
- **Algorithm**:
  - The actual core of the EMS.
- **Connectors**:
  - Allowing to connect the EMS to the devices.
- **Devices**:
  - The physical devices that are connected to the EMS.

## Tech Stack
- Python 3.12+, paho-mqtt 2.1.0, colorlog 6.9.0, jsonschema 4.23.0, influxdb-client 1.50.0
- Optional extras, one file each, none of them ever in `requirements.txt`: `requirements-api.txt` (fastapi + uvicorn — the `rest_api` service), `requirements-modbus.txt` (pymodbus — the `modbus_tcp` connector), `requirements-homeassistant.txt` (websocket-client — the `home_assistant` connector), `requirements-lora.txt` (pyserial — the `lora` serial connector; the `lorawan` one needs nothing, it is MQTT). `requirements-dev.txt` pulls in all four
- Entry point: `main.py` — run with `python main.py`
- Config: `config.json` validated against `config.schema.json` (JSON Schema Draft 2020-12). It, the root schema and every plugin schema are read with `encoding="utf-8"`, never the platform default — on Windows that is cp1252, which turned every non-ASCII device name into mojibake and crashed on a schema byte cp1252 leaves undefined; `tests/test_config.py` simulates that default so the rule holds on a UTF-8 CI too

## Project Structure
- `api/` — Abstract base classes (Connector, Device, Algorithm, Service, Parser, DevicesAccess) + capability interfaces (EnergyMeter, Switch, MetricSource) + the Stoppable cooperative-stop mixin + `options.py` (never-raising option coercion for plugin constructors) + `testing.py` and `conformance.py`, the internal, **not yet supported** test kit: axis-generic doubles, the threading harness, and the schema/constructor/loader checks, extracted so a plugin outside this checkout can run what the shipped ones run. Neither may import `pytest` or any axis package — `tests/conftest.py` keeps every fixture and the four concrete-device factories for exactly that reason
- `config/` — Config loader, schema validation, enums
- `connectors/` — Protocol implementations (MQTT, HTTP polling, Modbus TCP, Home Assistant WebSocket, OpenEMS Edge REST subclassing the HTTP one, LoRaWAN-via-network-server subclassing the MQTT one, point-to-point LoRa over a serial radio, pseudo file replay)
- `devices/` — Device implementations (P1 meter, Shelly Plug S, generic Modbus register-map meter, Home Assistant entity, OpenEMS channel view, generic LoRa node with a config-driven payload map, pseudo — each of the middle four paired with a `*_switch` subclass, see the capability note below)
- `algorithms/` — Energy management logic (AutoToggle, DeviceChecker)
- `parsers/` — Data parsers (OBIS for P1 meters with CRC16-ARC)
- `devices_manager/` — Thread-safe singleton device registry
- `simulation/` — The replay clock: event time vs committed step time, plus the lockstep barrier
- `storage/` — Storage backends (CSV file, null, InfluxDB 2.x with batching + Flux reads)
- `storage_manager/` — Storage fan-out with per-backend error isolation
- `supervisor/` — Thread supervision: restart policy + worker lifecycle
- `services/` — The fifth plugin axis: supervised workers that own no devices (read-only REST API)
- `__metaclasses/` — Singleton patterns

## Key Patterns
- Plugin architecture: classes loaded dynamically from config via module name convention (documented in `CONTRIBUTING.md`; per-plugin option schemas in `<axis>/*.schema.json`, on all five axes). The name may be dotted: `"<vendor>.<name>"` resolves to `<axis>/<vendor>/<name>.py` and `<axis>/<vendor>/<name>.schema.json`, which is how a plugin published outside this repository loads. **That config string is frozen** — `config.json` is mounted read-only so upgrades never ask an operator to rewrite it, and the bare `<vendor>.<name>` form survives a later move to a `sys.path` root, a `motrix_edge/` package or wheels, which a `community.` prefix would not. `_PLUGIN_NAME` in `config/config.py` is the **only** traversal guard on that value, because `files(package).joinpath()` performs no containment check; keep `.fullmatch`, and never widen the regex without widening the `joinpath` in the same edit (the regex alone turns a silent skip into a silent miss)
- **`config.json`'s `version` is the config *document format*, never the EMS release** — this project has no release constant, and the file is mounted read-only. It is compared against `CONFIG_FORMAT_VERSION` in `config/version.py`; the key is optional and its **absence is not a claim** (`Config.version` is `None`, agreeing with what the viewer's `topology.ts` reports for the same bytes). A newer minor warns, either major mismatch is an ERROR, and none of it is fatal — `Config` is built in `Main.__init__`, *before* `main()`'s `try/finally`, so it has no shutdown path to raise into. Plugin options are versioned by their own `*.schema.json`, never by this number. The two conflated jobs of the old `DEFAULT_VERSION` — "assumed when absent" and "compared against" — are what made a silent file pass while the project's own worked example was warned about; do not merge them again
- **A device refuses a protocol it cannot serve; it never raises.** It *declares* what it serves — `SUPPORTED_PROTOCOLS` on the class, plus `UNSERVABLE_PROTOCOLS`/`PROTOCOL_REFUSAL` where a generic sentence would not help — and `Device.__init__` logs one ERROR at startup on the main thread while `refuse_unserved_protocol()` returns `False` per payload. No device carries a `match` on `protocol` any more, so the declaration is the single source of truth, and `tests/test_device_protocol.py` sweeps every class to keep it so. A device that dispatches on no protocol declares nothing (`devices/pseudo.py`). A raise in `__init__` is now contained — `main.create_classes` logs the traceback and skips that one entry — but a skipped device is one that silently does not exist, which is worse than one that visibly never reports, so nothing on that path may raise, including on an unhashable `protocol` that JSON can supply. P1 also ships **no** default topic, subscription or pattern: it has only addressing options, there is no standard P1-over-MQTT topic, and a synthesised one would file another meter's telegram under this device's name rather than failing loudly
- **`Connector.deliver()` is the one guarded boundary between a connector and a device**, and the only place a connector calls `receive()`. A device exception used to end the whole run: it escaped the supervised `start()`, spent the restart budget, marked the worker finished, and `main` — which waits on connectors — read that as "all connectors finished". Behind `connectors/mqtt.py` it was quieter and no better, dying on that connector's dispatch thread through `threading.excepthook`, past every configured handler. `deliver()` logs it with the traceback, rate-limits the repeat, marks the device connected-but-not-ready and drops the reading. Everything else in `connectors/` stays narrow on purpose: the rule is *whose frame is in the `try`* — broad only where a plugin's is
- **`connectors/mqtt.py` dispatches per device, bounded and in order** — one `queue.Queue(maxsize=64)` and one dispatch thread per device that actually receives traffic, created on its first matching message and inherited verbatim by `connectors/lorawan.py`. Both properties are load-bearing and neither is a performance concern. **Bounded**: a thread per *message* made the thread count a function of broker traffic — a retained-message flush on reconnect, a `subscription` of `#`, a chatty gateway — none of them things the EMS decides; a thread per *device* is a function of `config.json`. **Ordered**: two threads for one device could interleave inside `Device.receive`, which writes `self.data` wholesale, so an *older* reading could land last and reach the algorithms and the versioned CSV through `Connector.on_device_data_received` — a stale value presented as current, which is a correctness bug for a meter. Nothing on the enqueue path may block, because `on_message` runs on the thread `loop_forever()` owns and that thread answers PINGREQ; a full queue therefore drops the **oldest** payload (the newest is the closest thing to the present state, and dropping from the head leaves the rest in arrival order) and says so once per overflow episode. `stop()` releases the dispatchers without waiting — `Supervisor.stop_all` calls `request_stop()` on every worker before joining any — and the bounded join lives at the end of `start()`
- Supervised concurrency: each connector/algorithm runs in its own supervised daemon thread, with three outcomes — a crash is logged with its traceback and restarted with bounded backoff; a clean return is not restarted; a `SystemExit` (a library calling `sys.exit()` on a worker thread) is logged CRITICAL and deliberately **not** restarted, because a worker that exits has given up rather than failed. `_finished` is set from a `finally`, so even a `BaseException` unwinding through `_run` cannot leave `main` polling a worker that will never finish (`supervisor/supervisor.py`, tuned via the config `runtime` block). **A crash under a replay costs time, never a timestep** (while each backoff stays under `step_timeout_seconds`; the backoff doubles and is never reset, so `max_restarts` >= 6 or `backoff_seconds` >= 30 reaches the loud timeout and skips steps): `Algorithm.loop()` leaves the lockstep barrier when it returns but not when it raises, so the replay waits at the next step for the restart instead of running ahead through the backoff (which, at `speed: 0`, skipped a timing-dependent number of steps). The step it died on is still acked and never re-run, and the restarted `loop()` inherits whether it had been replaying (`_stepped_before_crash`), so a crash on the final timestep cannot restart into a reset clock and run live. What releases the replay when no restart is coming is `SupervisedWorker._retire()`: once, on every final exit and never between a crash and its restart, it calls the worker's duck-typed `retire()`, and `Algorithm.retire()` leaves the barrier
- Graceful shutdown: SIGTERM/SIGINT → `stop()` on every worker (`api/stoppable.py`), bounded join, then `StorageManager.close_all()`; workers poll `is_stopping()` and sleep via `wait_stop()`
- Device readiness: `threading.Event` for data_ready and connected states
- Bidirectional control: `device.control(cmd)` → `connector.send(device, cmd)`. Every frame of that chain returns `bool` — did the command reach a transport — and `Algorithm.control_device` gates the decision row on it
- Config-driven wiring: connectors receive devices via `inject_devices()`
- Capability interfaces: algorithms `isinstance`-check capabilities from `api/capabilities.py` (EnergyMeter, Switch), never concrete device classes — devices implement them (e.g. `P1(Device, EnergyMeter)`). `MetricSource` is the device→storage variant: a device names its own readings when its payload structure carries meaning (P1 keys by OBIS code, not list position)
- **`Switch` only on a class that is genuinely writable.** It is a type claim algorithms act on directly — `algorithms/auto_toggle.py` selects actuators with `isinstance(device, Switch) and device.data`, with no `is_writable` check — so a read-only device subclassing it is picked as an actuator and commanded every tick. `Device.control` **warns and answers `False`** rather than raising when the device is not writable, and `Algorithm.control_device` records a decision only when the chain answered `True` — which is what keeps the false row out of `algorithm_decisions.csv` and the versioned storage contract clean. That gate does not fix the algorithm's own belief that it holds an actuator, and deriving `is_writable` per instance cannot help because `isinstance` is class-level. Hence the `*_switch` subclasses: `modbus_switch`, `ha_switch`, `openems_switch`, `lora_switch`
- Optional dependencies at module top: a plugin needing a library outside `requirements.txt` imports it at module top so `main.create_classes` catches the `ModuleNotFoundError` and logs one per-entry skip — the same import inside a supervised `start()` is a crash loop, and once the restart budget is spent the worker counts as finished, which shuts the whole run down. Tests for such a plugin guard with `pytest.importorskip("<dep>")` **before any project import**, or a bare `ModuleNotFoundError` aborts collection for the entire suite
- Deterministic replay: the pseudo connector advances an **event clock** before dispatching each entry (what storage stamps readings with) and commits a **step clock** after the whole timestep (what triggers algorithms), then blocks on `simulation/clock.py`'s barrier until every algorithm has finished that step — so `speed=0` means "as fast as the algorithms allow". An algorithm joins that barrier in its **constructor**, so `main.create_classes` (`_construct`) withdraws whatever joined during a construction that raised: a skipped algorithm must never be a participant the replay waits `step_timeout_seconds` for on every step — or forever with `null`
- Liveness is connector-shaped: `main` waits on the connectors only, so a service (a supervised worker owning no devices) never keeps a finished replay alive — that is why the read-only API is a fifth axis and not a `Connector` with stub methods. A config with services and no connectors exits immediately, with a warning
- Read-only introspection: `services/rest_api.py` serves `/health`, `/devices`, `/devices/{name}`, `/workers`, `/decisions` in-process, for the live state that never reaches storage (readiness, capabilities, restart counts, barrier progress). Every payload is an explicit field allowlist — never `vars(obj)`, because a device snapshot shares the live connector and would reach its password
- Decision history is **core state, not a storage backend**: `api/decisions.py`'s `DecisionLog` singleton is written from `StorageManager.write_algorithm_decision` — the one funnel every backend already sees, so `/decisions` and `algorithm_decisions.csv` hold the same decisions in the same order by construction. The append sits *outside* `_fan_out`, so decisions are recorded even with zero storage backends configured; a ring-buffer *backend* would instead have made the endpoint's existence depend on an unrelated `storage` entry. The cursor is a monotonic per-process `seq`, never a timestamp — under `speed=0` every decision in one timestep carries the identical committed step time

## Key Documents
- `CONTRIBUTING.md` — plugin conventions and all five extension recipes (connector, device, storage, service, algorithm)
- `docs/storage-format.md` — **normative** contract for the CSV output, versioned by `STORAGE_FORMAT_VERSION`; the interface the external Motrix Edge View app consumes. `examples/` holds the byte-exact golden fixture, and `tests/test_storage_contract.py` fails when it moves
- **The viewer's nginx is the only authentication in this system.** The `viewer` compose profile gates `/api/*` with Basic auth and proxies to `edge:8000` across `motrix-net`, which is why the API port is not published, why `services/rest_api.py` ships no CORS middleware and no auth of its own, and why uncommenting the `ports:` block on `edge` puts an ungated copy of every route beside the gated one. The service's own docstring names the right trigger for changing that: *publish the port and authentication becomes the first thing to add here* — a condition that has not been met
