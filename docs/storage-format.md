# Storage output format

**Storage format version: `1.0`**
*(source of truth: `STORAGE_FORMAT_VERSION` in `storage/csv_file.py`; mirrored in
`examples/MANIFEST.json`. `tests/test_storage_contract.py` keeps the three in lockstep.)*

This document is normative for anything **consuming** EMS output — most immediately the
[Motrix Edge View](https://github.com/Motrix-Energy/motrix-edge-view) app, which is a separate repository in a different
language. `CONTRIBUTING.md` is the document for people *writing* plugins; this one is for
people *reading* what they produce.

Scope: the two CSV files written by `storage/csv_file.py`. The InfluxDB backend's shape
(flattened, all-float, aware-UTC timestamps, exclusive `stop` bound) is a different
contract, documented in `storage/influxdb.py`'s own `read()` docstring.

A worked, byte-exact example lives in [`examples/`](../examples/README.md). That fixture
is the interface: it is regenerated by running the EMS, and a contract test fails if the
bytes move.

---

## 1. The two files

| File | Written when |
|---|---|
| `device_data.csv` | a device accepts a payload (`Connector.on_device_data_received`) |
| `algorithm_decisions.csv` | an algorithm sends a control command (`Algorithm.control_device`) |

Both land in the backend's `output_dir` (default `data/storage`). Neither exists until
its first write — see §3.

### Headers, byte-exact

```
timestamp,device_name,data_json
timestamp,algorithm,device,command
```

Column order is part of the contract. A consumer may key by name, but a consumer that
positionally indexes is also entitled to rely on this order.

## 2. Dialect

Python's `csv` module defaults, with `newline=""` so the module — not the platform —
controls the terminator:

| Property | Value |
|---|---|
| Delimiter | `,` |
| Quote character | `"`, doubled when literal (`""`) |
| Quoting | `QUOTE_MINIMAL` — a field is quoted only if it contains `,`, `"`, `\r` or `\n` |
| Line terminator | **`\r\n`, on every platform** |
| Encoding | UTF-8, no BOM |
| Escape character | none — quoting is the only mechanism |

Two consequences worth stating outright:

- **A logical row can span physical lines.** A quoted field may contain a raw `\r\n`
  (see §6). Splitting the file on newlines is wrong; use a real CSV parser.
- **UTF-8 is not decorative.** Device and algorithm names are operator-chosen free text
  and routinely non-ASCII. Decoding as cp1252 or latin-1 produces mojibake, silently.

## 3. The header is written lazily

`CsvFileBackend` writes the header only when the file is **absent or zero bytes**. Three
consequences:

1. **No writes means no file.** A run in which no algorithm ever acted produces no
   `algorithm_decisions.csv` at all. A consumer must read *missing* as *no data*, never
   as an error, and never as a reason to abort loading the other file.
2. **A pre-existing empty file gets a header** on the next write. That is the state a
   `touch` or a truncating disk leaves behind.
3. **Appending across runs yields one header and interleaved timestamp domains.** Restart
   the EMS against the same `output_dir` and the second run appends. This is the normal
   operator experience, not an edge case, and it is the direct cause of §4.

## 4. Timestamps — read this part twice

### Two clocks, by design

`device_data.timestamp` is **event time**: the moment the reading was produced
(`SimulationClock.get_event_time()`). Under a replay that is the timestep currently being
dispatched, so a reading is filed against its own entry.

`algorithm_decisions.timestamp` is **committed step time**
(`SimulationClock.get_step_time()`): the timestep the algorithm was processing. A decision
computed while processing T belongs to T even if the replay has already moved on.

Both fall back to `datetime.now()` when no replay is driving the clock. The two files are
therefore joinable on `timestamp` — every reading for a timestep and every decision
derived from it carry the same value.

### The format is `datetime.isoformat()`, and it is not fixed-width

- Microseconds appear **only when non-zero**: `2024-01-15T10:00:00` and
  `2026-04-05T13:06:39.284157` are both normal.
- A UTC offset appears **only when the source datetime carried one**.
- The date/time separator is always `T`.

### The column is not a single time domain

This is the sharpest edge in the whole format, and it is systematic rather than rare:

- A **live** run stamps `datetime.now()` — naive, **local to the machine that wrote the
  file**, no offset.
- A **replay** stamps whatever the replay file carried, which may or may not carry an
  offset.
- One file routinely holds both. Wall-clock rows appear at the **head** of a run (before
  the replay publishes its first timestep) and at the **tail** (after `SimulationClock.reset()`),
  with replay rows between. Append two runs to one directory (§3) and the domains
  interleave outright — `examples/auto_toggle/expected/device_data.csv` is 36 naive rows
  followed by 18 offset-aware ones, thirteen weeks apart.

**Consumer rule.** Parse as ISO-8601. When an offset is present, honour it. When it is
absent, interpret the value as **local to the machine that wrote the file** — which is
what `storage/influxdb.py` does when it converts naive stamps for InfluxDB — and surface
the ambiguity rather than silently assuming UTC. Offer the reader a way to override the
assumed zone; you cannot recover the information from the file.

**JavaScript traps**, since the first consumer is a browser:

| Expression | Result |
|---|---|
| `Date.parse("2024-01-15T10:00:00")` | **local** |
| `Date.parse("2024-01-15")` | **UTC** — same instant in Python, an hour or more apart here |
| `new Date("2026-04-05T13:06:39.284157")` | six fraction digits; the ES grammar allows three, so this falls to the engine's implementation-defined parser |

Parse the string yourself.

### Rows are not guaranteed monotonic

Several connector threads append under one lock, so file order is **write order**, not
event order. Sort on read. Duplicate `(timestamp, device_name)` pairs are legal for the
same reason.

## 5. `data_json`

`json.dumps(device.data)` — the device's payload, verbatim. Deliberately **not**
`MetricSource.get_metrics()`: this backend serialises the payload, where the InfluxDB
backend turns structure into schema and therefore has to prefer the device's own naming.

**There is no schema.** Each device kind decides its own shape, and a third-party device
may emit anything `json.dumps` accepts. The three shipped kinds illustrate the range:

```jsonc
// pseudo — double-encoded: `payload` stays a JSON *string*, `parsed` is the decoded object
{"topic": "sensors/zone/temperature", "payload": "{\"value\": 15.2}", "parsed": {"value": 15.2}}

// shelly_plug — flat, and its numbers are strings
{"power": "118.4", "status": true}

// p1 — nested, and keyed by *position*: data[3] is a different register the moment the
// meter emits a different number of lines
{"model_id": "ISK", "data": [{"obis": {"medium": 1, "channel": 0, "class": 1,
  "instance": 8, "attribute": 1}, "data": [{"value": 480.0, "unit": "kWh"}]}], "crc16": 47822}
```

Hazards:

- **Unbounded depth and unbounded size.** Nothing caps either.
- **Keys may contain `.`**, which collides with dot-path flattening (§7). The collision is
  **not resolved**: last write wins, and dot-paths are not invertible. Do not rely on
  reconstructing the original structure from a flattened key.
- **Historic files may contain bare `NaN` / `Infinity` / `-Infinity`.** `json.dumps`
  defaults to `allow_nan=True`, so any non-finite float in a payload produced invalid JSON
  until this backend started serialising strictly (format 1.0). Files written earlier
  still contain it, and it costs a naive consumer the *whole row's payload* rather than
  the one field. From 1.0 onward a non-finite value is written as the string `"nan"`,
  `"inf"` or `"-inf"` — the same encoding `services/rest_api.py` already uses, so both
  surfaces agree.

## 6. `command`

**An opaque string.** Not necessarily JSON:

- `AutoToggle`, the project's public worked example, emits the bare strings `on` and
  `off` on every row.
- Other algorithms emit JSON objects.

Try-parse and fall back to the raw string. It may contain commas, quotes and newlines, so
a quoted `command` is the one field that can make a logical row span physical lines —
`data_json` never can, because `json.dumps` escapes control characters.

## 7. Gaps mean something

A row is written **only when the device accepted the payload**. A device that returns
`False` from `receive()` — an unreadable telegram, a topic it does not model — produces
**no row at all**.

That is deliberate: republishing the previous reading under a new timestamp would turn a
stalled or corrupt meter into a flat line in storage instead of the gap it actually is,
which is the more expensive lie because it looks like evidence.

So: **absence means "no reading received"**. It does not mean unchanged, and it does not
mean zero. Break the line at a gap; do not interpolate across it.

What the files *cannot* tell you is the difference between a device that is silent and a
device that was never configured. That is what the REST API's `/devices` and `/health` are
for.

## 8. What is not in the files

No device kind, no class, no connector, no protocol, no units, no configuration. **Names
are the only join key**, and they are operator-chosen free text — spaces, slashes, commas,
quotes and non-ASCII are all legal. (The REST API routes `/devices/{name:path}` rather
than `{name}` for exactly this reason.)

## 9. The control log is not one of these files

`PseudoConnector` accepts an optional `control_log` and writes a **third** file that is
*not* CSV:

```
2024-01-15T10:00:00,shelly_plug,off
```

No header. No quoting. Written with a raw `f.write` in text mode, so its line terminator
is **platform-translated** (CRLF on Windows, LF elsewhere) rather than the CSV files'
guaranteed CRLF. Every JSON command contains commas, so a CSV parser mis-splits it, and a
command containing a newline corrupts the line entirely.

It is a **debug log, not an interchange format**. When a `csv_file` backend is configured
it duplicates `algorithm_decisions.csv`; when one is not, it is the only record. A
consumer should recognise it and decline to parse it as CSV; if it must, split on the
first two commas only.

## 10. Flattening and numeric detection — one rule, two implementations

A consumer that charts arbitrary payloads has to flatten them, and the EMS already does
this in `storage/influxdb.py`. That makes it the one genuinely duplicated rule between the
repositories. **Two implementations of one rule is acceptable; two that drift silently is
not** — so the rule is stated here normatively, with the Python as reference.

**Flattening.** Recurse into dicts and lists. Join path components with `.`, and use a
list index as a path component: `{"a": [10, 20]}` → `{"a.0": 10.0, "a.1": 20.0}`. Stop at
depth 10 and stringify below that.

Two caveats specific to this format:

- `.` as a separator is ambiguous against keys that already contain `.` (§5).
- Positional indices are unstable for `p1`. `P1.get_metrics()` exists to solve this and
  keys by register instead, using **brackets** for repeated codes (`gas_m3[0]`) precisely
  because an OBIS code already contains dots. A consumer flattening `data_json` directly
  gets the positional form and should expect it to shift between messages.

**Type rules, in this order:**

1. `null` → no field.
2. `bool` → boolean. **Check this before number**: in Python `bool` subclasses `int`, and
   in JavaScript `Number(true) === 1`. A relay's on/off state must not become a 0/1 series
   by accident.
3. `int` / `float` → **float**. Always widen: InfluxDB pins a field's type on first write,
   and `parsers/obis.string_to_type` returns `int` or `float` depending on whether the
   meter printed a decimal point, so the alternation is guaranteed in production.
4. Non-finite (`NaN`, `±Infinity`) → **no field**. Not zero.
5. `str` → a number **only if** it full-matches, after stripping:

   ```
   [+-]?(?:\d+\.?\d*|\.\d+)(?:[eE][+-]?\d+)?
   ```

   otherwise a string. This matters because `shelly_plug` stores `{"power": "118.4"}`,
   which is useless as a string.

**Why the regex rather than the language's own parser.** It is deliberately stricter than
`float()` and far stricter than `Number()`:

| Input | `Number()` | This rule |
|---|---|---|
| `""` | `0` | string |
| `" 12 "` | `12` | number (leading/trailing whitespace is stripped first) |
| `"0x10"` | `16` | string |
| `"1_0"` | `NaN` | string — but `float("1_0")` is `10.0` in Python |
| `"Infinity"` | `Infinity` | string |
| `"nan"` | `NaN` | string |

A port written as `!isNaN(Number(v))` drifts from this on day one — a device id of `"1_0"`
or `"0x10"` silently becoming a number is the kind of bug that never gets found.

Note that `csv_file` itself never flattens; it serialises the payload verbatim. This
section is normative for the *consumer*, and `storage/influxdb.py` is the reference
implementation.

## 11. Versioning

`STORAGE_FORMAT_VERSION` lives in `storage/csv_file.py`.

| Bump | When |
|---|---|
| **MAJOR** | a header, column set or column order changes; the dialect changes; the timestamp format changes; or `data_json` / `command` change meaning |
| **MINOR** | additive only — a new column appended at the end, or a new optional file. A consumer built for `1.x` keeps working |

**The version is deliberately never written into a CSV.** A version row or comment line
would break every naive `DictReader` and PapaParse consumer — exactly the audience it
exists to protect. A format version is a property of the writer, not of a row. It is
published through `examples/MANIFEST.json`, which a consumer vendors alongside its copy of
the fixture.

### What makes a change visible on both sides

1. `tests/test_storage_contract.py` regenerates the golden fixture and compares it
   byte-for-byte. Any format change fails CI.
2. Its failure message names the cross-repo consequence: bump the constant, run
   `python examples/generate.py`, update this document, and open an issue on Motrix Edge View to
   re-vendor its fixture.
3. A lockstep assertion pins the constant, `examples/MANIFEST.json`, and the version line
   at the top of this file together, so bumping one without the others also fails.

Cross-repository synchronisation stays a **human step triggered by that issue**. There is
no submodule and no CI federation between the two repositories — the version boundary is
the fixture and the image tag, deliberately.
